# Arquitectura — portable-editor

Documento de referencia para mantener el proyecto. Si vas a tocar código, leé primero esto: acá están las decisiones, los invariantes y las trampas que no son obvias leyendo el código.

## Identidad del producto

Editor de escritorio (Linux/macOS) de **un archivo a la vez**. Liviano, arranca rápido, y lo suficientemente potente para uso diario de un dev. La identidad es ser mini: **no** se agregan tabs multi-archivo, árbol de archivos, LSP/autocompletado, git integrado ni sistema de plugins. Cualquier feature nueva se evalúa contra esa identidad.

Idiomas: **código, comentarios y strings de UI en inglés; documentación en español.**

## Stack y capas

```
┌────────────────────────────────────────────────┐
│ Frontend (webview)                             │
│   TypeScript vanilla + Vite                    │
│   CodeMirror 6 (motor de edición)              │
├────────────── IPC (invoke/events) ─────────────┤
│ Backend nativo (Rust)                          │
│   Tauri 2 + plugins: dialog, single-instance   │
│   IO de archivos, mtime, argv, eventos del OS  │
└────────────────────────────────────────────────┘
```

- **Sin frameworks de UI** (React, etc.): la UI es un editor y una status bar; no se justifica.
- El frontend nunca toca el filesystem directamente: todo pasa por comandos Rust.

## Superficie IPC

### Comandos (frontend → Rust, vía `invoke`)

| Comando        | Firma                                  | Notas                                                       |
| -------------- | -------------------------------------- | ----------------------------------------------------------- |
| `read_file`    | `(path: String) -> Result<DecodedFile>` | `DecodedFile = { contents, encoding, eol, mixed_eol, likely_binary, mtime }` (`mtime` del mismo stat que el chequeo de tamaño, ANTES del read — trampa #44). Chequea tamaño vía metadata primero: rechaza sin leer si supera `text_io::MAX_FILE_SIZE_BYTES` (100 MB). Detección: BOM (UTF-8/UTF-16) → UTF-8 estricto → fallback Windows-1252. `contents` siempre viene normalizado a `\n`. `eol` es mayoría de línea (no "¿aparece CRLF en algún lado?"); `mixed_eol` avisa cuando el archivo mezclaba LF y CRLF, cualquiera sea el que ganó. `likely_binary` (NUL en los primeros 8000 bytes) — ver trampa #9. |
| `write_file`   | `(path, contents, eol: String) -> Result<u64>` (mtime ms) | **Atómico** (`fs_ops::write_atomic`): temp (creado ya con el modo del original) + `sync_all` + rename, preserva permisos del original. Restaura `eol` (`"LF"`/`"CRLF"`) antes de escribir. Política: **siempre UTF-8 en disco**, sin importar el encoding de origen. Escribe a través de symlinks (`resolve_symlink_target`), no los reemplaza — trampa #15. |
| `file_mtime`   | `(path) -> Result<u64>`                | Millis desde epoch; usado por el polling de cambios externos |
| `startup_file` | `() -> Result<Option<StartupTarget>, String>` | `StartupTarget = { path, exists, extra_ignored }` (`extra_ignored`: archivos descartados en un "Open With" multi-selección, trampa #31). Prioridad: PendingFile (macOS "Open with", `exists` siempre `true`) > argv[1] (resuelto con `resolve_open_arg`, `exists: false` si el path todavía no existe) |
| `install_cli_command` | `() -> Result<String>`          | Solo macOS (error explicativo en otras plataformas). Symlink de `current_exe()` a `/usr/local/bin/portable-editor`: intenta sin privilegios primero, si falla pide admin vía `osascript` con `quoted form of` (no interpola paths directo en el script — ver trampa #17) |
| `save_recovery` | `(path, contents) -> Result<()>`    | Dump (no atómico) a `app_data_dir()/recovery/<hash(path)>.recovery` (directorio 0700, archivo 0600). Llamado cada 10 s si `doc.dirty` (`AUTOSAVE_INTERVAL_MS` en `main.ts`) |
| `read_recovery` | `(path) -> Result<Option<String>>` | `None` si no hay recovery para ese path |
| `clear_recovery` | `(path) -> Result<()>`             | Best-effort (ignora si no existe); se llama tras guardar o al descartar cambios explícitamente |
| `signal_ready` | `()`                                | Imprime `PORTABLE_EDITOR_READY` a stdout (con flush explícito) al final de `init()`. Solo para benchmarking de arranque (`scripts/bench-startup.sh`) — no lo usa nada en runtime |

### Eventos (Rust → frontend, vía `emit`/`listen`)

| Evento      | Payload  | Emisores                                                            |
| ----------- | -------- | ------------------------------------------------------------------- |
| `open-file` | `StartupTarget` (`{ path, exists, extra_ignored }`) | 1) `RunEvent::Opened` en macOS (app corriendo, `exists` siempre `true`; `extra_ignored` > 0 si Finder mandó más de un archivo — ver trampa #31), 2) callback de single-instance (segunda invocación CLI, vía `resolve_open_arg`, `extra_ignored` siempre 0) |
| `menu-action` | `string` (id del ítem: `"new"`\|`"open"`\|`"save"`\|`"save_as"`\|`"shortcuts"`) | `on_menu_event` en `build_menu()`, ante click o accelerator de un ítem del menú nativo |

Todo camino de apertura del frontend converge en `openFile()` de `main.ts` (archivo existente) u `openNewFileAt()` (path que todavía no existe — CLI/"Open with..." a un archivo por crear), ambos con el guard de cambios sin guardar. **No crear caminos alternativos que llamen a `read_file` sin pasar por `openFile()`** (única excepción: `restoreSession()` y `reloadFromDisk()`, que se saltan deliberadamente esos guards de confirmación — no los diálogos de error, ver trampa #35).

## Estado

### En memoria (`main.ts`)

- `doc: DocState` (tipo en `document.ts`) — `{ path, dirty, mtime, encoding, eol, mixedEol, missing, indent, savedText, cursor, gen }`. Única fuente de verdad sobre el archivo abierto. `main.ts` no arma este objeto a mano: cada "convertirse en otro documento" es `becomeDocument(emptyDoc(...) | docFromFile(...) | docFromRecovery(...))` (bump de `gen` + `Object.assign` en un solo paso síncrono), y la recarga del mismo archivo es `Object.assign(doc, fromDisk(file, contents))`. La regla "buffer ≠ disco ⇒ dirty" (recovery aceptado) vive en `fromDisk`/`docFromRecovery`, no en los call sites. `encoding` es solo para mostrar en la status bar: tras cada guardado exitoso se resetea a `"UTF-8"` (política de guardado). `eol` sí importa funcionalmente: viaja de vuelta a `write_file` en cada guardado. `missing` lo pone `checkExternalChange()` cuando `file_mtime` falla (archivo borrado/renombrado); mientras esté en `true`, `saveFile()` se comporta como `saveFileAs()`. `indent` se re-detecta (`indent.ts`) en cada apertura/recarga; no persiste entre sesiones — es una propiedad del archivo, no una preferencia global.
- `doc.savedText` — contenido tal como quedó en el último load/save; baseline contra el que `nextDirty()` compara un undo/redo para limpiar `dirty`. `null` si no hay disco al que volver (untitled o path inexistente).
- `doc.cursor` — última posición conocida, alimentada por el callback `onCursorMoved`.

### Persistido (localStorage, prefijo `portable-editor:`)

| Key                          | Contenido                                  |
| ---------------------------- | ------------------------------------------ |
| `portable-editor:theme`      | id del tema                                |
| `portable-editor:font-size`  | tamaño de fuente (9–28)                    |
| `portable-editor:wrap`       | `"true"`/`"false"`                         |
| `portable-editor:recent`     | JSON `RecentEntry[]` (máx. 8): `{path, line, col}` |

Las entradas de recientes guardan el cursor; se sincroniza en `syncRecentCursor()` al cambiar de archivo y al cerrar la ventana. El primer elemento es el que se restaura al arrancar sin argumentos.

## Flujos clave

### Abrir archivo
`openFile()` → guard de dirty → diálogo nativo (o path directo) → `invoke read_file` → `editor.setText()` (estado nuevo: **descarta historial de undo a propósito**) → `afterFileLoaded()` (path, status, recientes, lenguaje, mtime).

### Guardar
`saveFile()`/`saveFileAs()` → `invoke write_file` (atómico, con `eol` de `doc.eol`), que **devuelve el mtime resultante**; `writeTo()` lo asigna a `doc.mtime` en el mismo tick que `dirty = false`. Antes se hacía un `refreshMtime()` después, y en el gap entre las dos llamadas el polling podía tomar el propio guardado como cambio externo (trampa #44). `writeTo()` resetea `doc.encoding` a `"UTF-8"` al terminar: el guardado siempre reescribe el archivo en UTF-8, así que mostrar el encoding original después sería mentir.

### Cambios externos
Poll cada 2 s + al enfocar la ventana (`checkExternalChange`):
- mtime distinto y **sin** cambios locales → recarga silenciosa con `editor.replaceText()` (preserva cursor e historial de undo).
- mtime distinto y **con** cambios locales → prompt. Se actualiza `doc.mtime` antes de preguntar para no repetir el prompt por el mismo cambio.
- `file_mtime` falla (archivo borrado o renombrado) → `doc.missing = true`, status bar muestra "(deleted on disk)", sin diálogo (no hay con qué interactuar). Si una siguiente poll vuelve a leer el mtime OK, se limpia solo. Mientras esté `missing`, `saveFile()` redirige a `saveFileAs()` en vez de reescribir un path que ya no existe.

Decisión: polling en vez de watcher nativo (`notify`). Es un solo archivo; un `stat` cada 2 s es gratis y evita una dependencia y el manejo de estado del watcher.

### Recuperación de crash (autosave)
Cada 10 s (`AUTOSAVE_INTERVAL_MS`), si `doc.dirty` y `doc.path !== null` → `invoke save_recovery`. No es atómico ni crítico: perder un dump a mitad de escritura solo significa recuperar un snapshot un poco más viejo la próxima vez, no corrompe nada real (a diferencia de `write_file`).

Al abrir un archivo (`openFile`, `restoreSession`, `openNewFileAt`) se compara el contenido recién leído del disco contra un posible recovery leftover (`checkRecovery`):
- Sin recovery, o igual al disco → se usa el disco tal cual, se limpia cualquier recovery viejo.
- Distinto → pregunta antes de usarlo. Si el usuario acepta, el contenido recuperado reemplaza al del disco y `doc.dirty` se fuerza a `true` (hay que guardarlo para que persista de verdad).

El recovery se limpia (`clearRecovery`) en tres momentos: guardado exitoso (`writeTo`), el usuario elige NO recuperar, o se abandona el documento actual al abrir otro (`confirmDiscard` pasa). **Alcance deliberado**: solo documentos con `doc.path` real. Un buffer 100% untitled (`Mod+N`, nunca asociado a un path) no tiene una clave estable entre lanzamientos de la app — si se pierde antes de guardar, se pierde. Ver ROADMAP para por qué no se cubre.

### "Open with..." del sistema
- **Linux**: el path llega por argv → `startup_file` lo resuelve.
- **macOS**: el path NO llega por argv; llega como `RunEvent::Opened` (AppleEvent). Dos casos:
  - App arrancando (`PendingFile.frontend_ready == false`): el evento llega antes de que el frontend escuche → se guarda en `PendingFile.slot` (estado managed), SIN emitir, y `startup_file` lo consume (y marca `frontend_ready`).
  - App corriendo (`frontend_ready == true`): se emite `open-file` y el frontend lo abre al toque, sin tocar el slot. Ver trampa #32.

### Instancia única
`tauri-plugin-single-instance`: la segunda invocación no abre ventana; su callback enfoca la existente y, si hay argv de archivo, lo resuelve contra el `cwd` de la segunda invocación y emite `open-file`.

El frontend, al recibir `open-file` (o el path de arranque en frío), llama a `openFile`/`openNewFileAt` con `external: true`. Eso activa `confirmExternalReplace()` además del `confirmDiscard()` de siempre: si hay un archivo real abierto (`doc.path !== null`), pregunta antes de reemplazarlo — **incluso sin cambios sin guardar**. Es la diferencia con una apertura in-app (botón, menú File, recientes): ahí no tiene sentido preguntar "¿reemplazar?" si no hay nada que perder, pero una apertura que llega desde afuera (otra invocación de CLI, "Open with...") puede interrumpir algo que el usuario está mirando sin haberlo pedido desde dentro de la app.

**Esto es un parche al síntoma, no una resolución del límite de fondo**: sigue existiendo una sola ventana posible (ver ROADMAP, "Hallazgos de revisión externa", ítem 3). Si en el futuro se decide soportar múltiples ventanas, `confirmExternalReplace()` deja de ser necesario para el caso "segunda invocación con archivo" (abriría ventana nueva en vez de preguntar) — no lo hagas más complejo de lo que es a la espera de esa decisión.

## Editor (`editor.ts`)

- CodeMirror se reconfigura en caliente con **Compartments**: `themeConfig`, `languageConfig`, `wrapConfig`. Para agregar otra opción dinámica, seguir ese patrón.
- `buildExtensions()` reconstruye las extensiones desde las variables de clausura (`currentTheme`, etc.) — necesario porque `setText` crea un `EditorState` nuevo y los Compartments vuelven a su valor inicial si no.
- `setText` vs `replaceText`: el primero resetea historial (abrir otro archivo); el segundo lo preserva (recarga del mismo archivo). No confundirlos.
- Detección de lenguaje: `LanguageDescription.matchFilename` sobre el **basename** (los regex de nombres tipo `Makefile` no matchean paths completos). La carga es lazy y hay un `languageToken` que descarta cargas que llegan tarde si el usuario cambió de archivo en el medio.
- La fuente es única y viene de variables CSS (`--editor-font`, `--editor-font-size`) aplicadas en `baseTheme`; el tamaño se cambia sin reconfigurar CodeMirror.

## Temas (`themes.ts`)

Para agregar un tema:
1. Definir una `ThemePalette` (todos los campos son obligatorios).
2. Agregar la entrada a `THEMES` con `buildTheme(palette, dark)`.
3. Nada más: el selector, la persistencia y el `data-dark` del body salen del registro.

`themeById()` es tolerante con un localStorage viejo: cualquier id desconocido cae a `DEFAULT_THEME_ID` (trampa #33). Solo lanza si ESE id no está en `THEMES` — invariante interno roto, no un dato externo.

## Trampas conocidas (no las "arregles" sin leer esto)

1. **Single-instance debe ser el PRIMER plugin** registrado en el Builder. Es requisito del plugin.
2. **Alt+Z usa `event.code`, no `event.key`**: en macOS `Alt+Z` produce "ω" y `event.key` no sirve.
3. **El guard `#[cfg(target_os = "macos")]` en `lib.rs`**: `RunEvent::Opened` no existe en Linux; sin el guard no compila. El `let _ = (app, event)` del branch contrario evita warnings de variables sin usar.
4. **Permisos IPC**: cualquier API nueva de `@tauri-apps/api` o de plugins puede requerir un permiso en `capabilities/default.json`. Si un `invoke` falla con "not allowed", falta el permiso ahí.
5. **El temp del guardado atómico** vive en el mismo directorio que el destino (mismo filesystem, si no `rename` no es atómico), nace con el modo del original (`OpenOptions::mode`), se re-aplican los permisos exactos (el `mode` inicial pasa por umask) y se hace `sync_all` ANTES del rename. Ver trampas #40 y #41.
6. **`onDocChanged` NO dispara en recargas programáticas.** `editor.replaceText()` despacha su transacción con `userEvent: "reload"`, y el update listener de `editor.ts` no llama a `onDocChanged` para transacciones marcadas así. La anotación es el seam correcto porque es el propio CodeMirror el que distingue "qué provocó este cambio" (`isUserEvent` ya se usa para `undo`/`redo`): el conocimiento de que un reload no es una edición vive en el mismo lugar que produce la transacción, en vez de que `main.ts` tenga que deshacer un `dirty = true` espurio después. `reloadFromDisk()` sigue haciendo `Object.assign(doc, fromDisk(...))` — no es un parche sobre `dirty`, sino la única escritura de los campos de disco (`dirty`, `encoding`, `eol`, `savedText`, ...) tras un reload. (Hasta 2026-08-25 era al revés: el llamador tenía que resetear `dirty` a mano.)
7. **`tauri dev` con argumento**: los args CLI se prueban con el binario compilado o `npm run tauri dev -- -- -- archivo.txt` (doble `--`). Ojo: el binario en `target/debug/` sigue dependiendo del servidor de Vite para cargar el frontend — si lo invocás directo desde otra terminal con `npm run tauri dev` ya detenido, la ventana abre en blanco (sin editor ni status bar, solo el título). No es un bug de la app, es nomás que no hay nada que cargar. No pasa con el bundle de release (frontend embebido, sin dependencia externa).
8. Las **asociaciones de archivo** solo existen con la app instalada desde el bundle; en dev no funcionan.
9. **La detección de Windows-1252 es una heurística de último recurso**, no un chardet real: si los bytes no tienen BOM y no son UTF-8 válido, se asume Windows-1252 porque nunca falla al decodificar (mapea todo byte a algún codepoint). Para textos legado que no sean de alfabeto latino (Shift-JIS, etc.) el resultado va a ser basura legible-pero-incorrecta, no un error. Es una decisión consciente de simplicidad (ver ROADMAP), no un bug.
10. **El chequeo de tamaño en `read_file` va antes de `std::fs::read`, no después.** El orden importa: es lo que evita cargar un archivo de varios GB a memoria solo para descartarlo. No "simplificar" juntando ambos pasos.
11. **No agregar `PredefinedMenuItem::quit` al menú sin resolver esto antes**: en Tauri, Quit saltea `onCloseRequested` y llama `exit(0)` directo — el guard de "cambios sin guardar" nunca se ejecuta. Bug conocido y abierto en Tauri (issues #3124/#7586/#13511). Por eso hoy no hay Quit en el menú.
12. **Cada accelerator del menú nativo (`build_menu`) es dueño único de su atajo — y esto aplica también contra los keymaps internos de CodeMirror, no solo contra el keydown handler de `main.ts`.** `Mod+N/O/S/Shift+S` fueron sacados a propósito del keydown handler de `main.ts` (evita doble disparo, ej. dos diálogos de "Save as" a la vez). Pero un accelerator nuevo puede chocar igual con un binding que CodeMirror ya trae de fábrica en `basicSetup` (`defaultKeymap`, `searchKeymap`, `historyKeymap`, etc.) sin que nadie lo note: el menú nativo reclama la key equivalent a nivel de sistema (AppKit en macOS, accel groups en GTK) ANTES de que el evento llegue al webview, así que CodeMirror ni se entera de que existía un binding suyo para esa tecla — no hay conflicto visible, el atajo de CodeMirror simplemente deja de andar. Pasó con `Mod+/` (trampa #21). Antes de asignarle un accelerator nuevo a un ítem de menú, chequear contra el código fuente instalado de `@codemirror/commands` (no de memoria), no solo contra `main.ts`.
13. **El panel de búsqueda de CodeMirror (`Mod+F`) se tematiza en `styles.css` (`#editor .cm-panel.cm-search`), no en `themes.ts`.** Es chrome del programa, no contenido del editor — mismo criterio que la status bar. No moverlo a `buildTheme()`: haría 4 variantes ligeramente distintas en vez de una consistente, y dejaría afuera a One Dark (no pasa por `buildTheme()`). El botón de cerrar (`button[name="close"]`) viene `position: absolute` del base theme de CM6; hay que pisarlo a `static` o `margin-left: auto` no hace nada.
14. **El botón de indentación de la status bar NO reconvierte el código existente**, solo configura cómo se indenta lo que se escribe de ahora en más (`indentUnit`). Es comportamiento estándar (VS Code también lo separa en un comando aparte) — no "arreglarlo" para que reformatee el documento sin evaluar primero el riesgo de corromper líneas de alineación (ver ROADMAP Fase 4, ítem 3).
15. **`write_file` escribe A TRAVÉS de los symlinks, no sobre ellos.** `resolve_symlink_target()` resuelve el target real antes del `tmp_path`/`rename` — si no existiera ese paso, el `rename()` reemplazaría el symlink mismo por un archivo plano (rompiendo dotfiles manejados con Stow/chezmoi/Nix). No "simplificar" quitando esa resolución.
16. **`Path::canonicalize()` requiere que el archivo YA exista** — falla con `NotFound` si no. Por eso `resolve_open_arg()` no lo usa solo: intenta `canonicalize()` primero y cae a `std::path::absolute()` (no toca el filesystem, no exige existencia) si falla. No volver a un `.canonicalize().ok()` pelado para resolver argumentos de CLI — eso es exactamente el bug que tenía antes (un `portable-editor archivo-nuevo.txt` se ignoraba en silencio).
17. **`install_cli_command` pasa el path del ejecutable a `osascript` como argv, no interpolado en el texto del script.** El AppleScript lo shell-quotea con `quoted form of` antes de meterlo en `do shell script ... with administrator privileges`. No "simplificar" volviendo a un `format!("... {path} ...")` armado a mano — eso corre con privilegios de admin, y un path con comillas rompería el escaping (command injection).
18. **El recovery de autosave va a `app_data_dir()`, no a `localStorage`.** Se evaluó `localStorage` (ya se usa para tema/fuente/wrap/recientes) y se descartó a propósito: es síncrono (bloquearía el hilo de UI en cada dump) y tiene límite de tamaño (~5-10 MB típico) — justo lo que rompería para los archivos de hasta 100 MB que Fase 3 ya soporta. No migrar el recovery a `localStorage` "por consistencia" sin releer esto.
19. **`cargo build --release` a secas produce un binario con la ventana en blanco.** La elección entre `devUrl` (servidor de Vite) y `frontendDist` (assets embebidos) la resuelve el CLI de Tauri al invocar la compilación — no es un `#[cfg(debug_assertions)]` en el código. Un `cargo build --release` corrido por afuera de `tauri dev`/`tauri build` NO usa el frontend embebido correctamente: abre una ventana sin nada, ni siquiera el HTML estático (botones de la status bar). Para probar/benchmarkear un binario de producción real sin el bundle completo: `npm run tauri build -- --no-bundle`. Ver `docs/RELEASE.md`.
20. **`println!` con stdout redirigido a archivo/pipe es block-buffered, no line-buffered.** Si el proceso muere por `kill -9` (sin shutdown limpio) antes de que el buffer se vacíe, el output se pierde entero — pasó con `signal_ready` hasta que se le agregó `stdout().flush()` explícito. Cualquier print pensado para ser leído por un script externo que mate el proceso necesita flush explícito.
21. **El accelerator de "Keyboard Shortcuts" es `Mod+Shift+/`, no `Mod+/`.** `Mod+/` es `toggleComment` en el `defaultKeymap` de CodeMirror — un menú nativo con ese accelerator se lo comía sin avisar (ver trampa #12), dejando "comentar línea" inalcanzable por teclado en las dos plataformas. No volver a `Mod+/` para este ítem.
22. **`detect_eol()` decide por mayoría de línea, no por "¿aparece CRLF en algún lado?".** La versión vieja hacía `text.contains("\r\n")`: un solo `\r\n` colado en un archivo mayormente LF (típico de pegar un snippet de Windows) convertía TODO el archivo a CRLF al guardar, generando diff-churn en git por una sola línea. `mixed_eol` (`text_io.rs`, `doc.mixedEol` en `main.ts`) expone cuando el archivo realmente mezclaba ambos estilos, sin importar cuál ganó el voto — se muestra en la status bar como "LF (mixed)"/"CRLF (mixed)". No volver a "any CRLF" para decidir `eol`.
23. **Todo flujo de usuario sobre el documento corre por UNA cola serial (`exclusive()` / `documentQueue` en `main.ts`), no en paralelo.** Nació (2026-08-25) solo para los eventos `open-file`: dos invocaciones CLI casi simultáneas corrían sus diálogos y mutaciones de `doc` en paralelo, con el orden dependiendo de qué diálogo cerraba primero el usuario — y descartar el segundo evento no era opción (no hay próximo poll que lo reintente). Ese mismo día se generalizó a New, Open (menú, botón, drop, recientes, CLI, "Open with..."), Save, Save As, `restoreSession` y el reload del poll — ver trampa #56 para el porqué. `exclusive(task)` encadena con `then(task, task)`: un flujo que falla no bloquea al siguiente.
24. **`recovery_key()` usa FNV-1a a mano, no `DefaultHasher`.** `DefaultHasher` documenta explícitamente que su algoritmo NO está garantizado estable entre versiones de Rust — un cambio de toolchain entre releases podría cambiar la clave de TODOS los recovery pendientes en silencio, dejando inalcanzable el recovery de un crash anterior a la actualización, sin ningún error visible. FNV-1a es aritmética pura, no puede cambiar por debajo. Costo aceptado y único: cualquier recovery YA pendiente en disco al momento de este cambio (creado con la clave vieja de `DefaultHasher`) queda huérfano una sola vez al actualizar — se consideró preferible a dejar el riesgo abierto indefinidamente hacia adelante. El test `key_matches_a_known_fnv1a_value` fija el algoritmo exacto: si hace falta cambiarlo de nuevo, que sea a propósito (con plan de migración), no un swap accidental de función de hash.
25. **`reloadFromDisk()` compara `doc.dirty` antes y después de su propio `await`.** Es la única espera adentro de la función (`invoke("read_file")`); si el usuario tipea mientras esa lectura está en vuelo, `doc.dirty` pasa a `true` a mitad de camino sin que nadie arriba se entere. Sobreescribir en silencio en ese caso perdía la edición nueva con nada más que un `Ctrl+Z` que el usuario no tiene motivo para intentar. El guard compara `dirtyBeforeRead` (capturado ANTES del `await`) contra `doc.dirty` DESPUÉS: si pasó de `false` a `true`, pregunta antes de pisar (mismo diálogo que `checkExternalChange()`, factorizado en `confirmReloadDiscard()`); si ya era `true` antes de entrar (la rama donde el caller ya preguntó y el usuario confirmó descartar), no vuelve a preguntar — sería un diálogo duplicado.
26. **El dirty flag se limpia solo en undo/redo que aterriza EXACTO en el contenido guardado (`savedText`), no en cualquier edición que por casualidad llegue al mismo texto.** `onDocChanged` en `editor.ts` distingue undo/redo de una edición normal vía `tr.isUserEvent("undo"|"redo")` (anotación real de `@codemirror/commands`, verificado contra el paquete instalado) y pasa el texto resultante ya calculado por CodeMirror — evita que `main.ts` tenga que llamar `editor.getText()` desde adentro de su propio callback de construcción (hubiera sido una referencia a `editor` en TDZ mientras `const editor = createEditor(...)` todavía se está evaluando). La comparación de string SOLO corre en undo/redo (raro comparado con cada tecla tipeada), no en cada `onDocChanged` — importa para archivos grandes, donde comparar en cada keystroke sería el mismo tipo de costo que ya se evita en `detectIndent`/highlighting. `savedText` es `null` para archivos sin path real (`newFile`, `openNewFileAt`): no hay un "guardado" al que volver, así que deshacer hasta vacío no debe limpiar el dirty ahí.
27. **`autosaveTick()` se re-limpia solo si un guardado real la superó mientras escribía.** El `clearRecovery()` de `writeTo()` es fire-and-forget (`void`, no `await`) — si un `autosaveTick()` ya estaba escribiendo contenido viejo justo cuando el usuario guarda, y esa escritura vieja termina DESPUÉS del `clear_recovery` del guardado exitoso, el recovery queda re-creado con contenido más viejo que lo ya guardado (ofrecería "¿recuperar?" apuntando a una versión anterior a la que ya está a salvo en disco). El fix: después de su propio `await`, si `doc.dirty` ya es `false` para el MISMO `path` que capturó al arrancar (no `doc.path` releído, que pudo cambiar por un Save As mientras tanto), es señal de que un guardado real terminó mientras escribía — se re-limpia. Llamar `clear_recovery` dos veces es inofensivo (`std::fs::remove_file` con el error ignorado, ver `lib.rs`).
28. **Todo acceso a `localStorage` pasa por `safeGetItem`/`safeSetItem` (`main.ts`), nunca `localStorage.*` directo.** `localStorage` puede tirar (storage deshabilitado, cuota llena, perfil corrupto) — igual de externo que un `invoke` de Tauri, que sí está guardado con `try/catch` en todos lados. Los dos helpers atrapan el error y degradan a "como si la clave no existiera": `parseFontSize`, `parseRecent` y `themeById` ya toleran `null`/basura, así que no hace falta tocar nada río abajo. Si agregás una preferencia nueva, usá los helpers — no `localStorage` pelado.
29. **`startup_file()` y el callback de single-instance toman el primer argumento CLI literal, sin filtrar nada que empiece con `-`.** Esta app no tiene NINGÚN flag propio (no hay `clap` ni parser de argumentos — el único argumento posible es la ruta del archivo), así que un filtro `starts_with('-')` no protegía contra ninguna colisión real: solo rompía en silencio abrir un archivo cuyo nombre real empieza con guion (`-notes.txt`, válido en Unix) y descartaba sin aviso cualquier cosa después de un guion suelto. Si en algún momento se agregan flags reales, la forma correcta de resolver la ambigüedad es el separador `--` estándar de Unix (`portable-editor -- -notes.txt`), no un filtro heurístico sobre el primer caracter.
30. **`install_cli_command` solo pide privilegios de admin si reemplazar el symlink realmente los necesita.** `std::os::unix::fs::symlink` falla con `AlreadyExists` en cada reinstalación (normal: ya corrió una vez antes), no solo cuando falta permiso — así que ese error por sí solo NO implica que haga falta `osascript`. Antes de caer al camino con privilegios, se chequea si lo que hay en `CLI_TARGET` es justamente NUESTRO symlink viejo (`symlink_metadata(...).file_type().is_symlink()`); si lo es, se borra y se re-crea sin pedir nada — mismo nivel de privilegio que crearlo la primera vez. Si hay otra cosa ahí (un archivo real, de otro programa), se deja intacto y cae al camino de `osascript` de siempre (que sí hace `ln -sf`, o sea que ESE camino sí lo reemplazaría — comportamiento preexistente, sin cambios).
31. **`StartupTarget.extra_ignored` es lo único que le avisa al usuario que "Open With" con multi-selección descartó archivos.** Finder manda TODAS las URLs seleccionadas en un solo `RunEvent::Opened` — portable-editor abre una sola por diseño (identidad "un archivo a la vez"), así que las demás siempre se descartan. Antes se perdían en silencio (`.next()` sobre el iterador, sin registrar cuántas quedaban). Ahora `paths.count()` sobre el resto del iterador (ya consumido el primer elemento por `.next()`) cuenta las descartadas, y `notifyExtraFilesIgnored()` en `main.ts` lo avisa con un diálogo simple DESPUÉS de abrir la primera — no antes, para no demorar la apertura que sí va a pasar. `PendingFile` pasó de guardar solo el path (`Mutex<Option<String>>`) a guardar el `StartupTarget` completo (`Mutex<Option<StartupTarget>>`): si solo guardara el string, `extra_ignored` se perdería en el camino frío de arranque (cuando `RunEvent::Opened` llega antes de que el frontend tenga el listener registrado, y el dato solo sobrevive vía `startup_file()` polling `PendingFile`).
32. **Toda entrada de "abrime este archivo" mientras la app corre — `RunEvent::Opened` en macOS y el callback de single-instance en ambas plataformas — pasa por `deliver_target` → `startup::merge_opened`, que decide emitir o guardar según `frontend_ready`, NUNCA según si el slot está vacío.** (La regresión de 2026-08-25: el primer Open With dejaba el slot ocupado y el segundo se fusionaba sin emitir.) `slot` y `frontend_ready` viven bajo UN solo `Mutex<PendingState>`: `startup_file()` hace `take_pending` (toma el slot y sube el flag) en la misma sección crítica, así un target que llega en paralelo cae en el slot o se emite — nunca ambos, nunca ninguno; antes eran un `Mutex` y un `AtomicBool` separados, correctos solo porque ambos corrían en el main thread. Con el flag en `false` (arranque frío) vale la fusión: se conserva el PRIMER target y se suma `1 + extra_ignored` del nuevo; tampoco se emite (el listener no existe, y emitir Y guardar abría el mismo archivo dos veces). Hasta 2026-08-25 single-instance emitía a ciegas y una segunda invocación CLI durante el arranque frío se perdía sin síntoma; ahora el flag es significativo también en Linux. `merge_opened`/`take_pending` son puras y testeadas (`startup.rs`).
33. **`themeById()` cae a `DEFAULT_THEME_ID`, no a `THEMES[0]`.** Coinciden hoy (los dos son One Dark), pero estaban cableados de forma independiente — reordenar `THEMES` en el futuro divergiría el fallback en silencio sin que ningún test lo note. Si `DEFAULT_THEME_ID` no está en `THEMES` (invariante interno roto, no debería pasar nunca), tira un `Error` explícito en vez de fallar en silencio — mismo criterio que `byId()` en `main.ts`.
34. **`detectIndent()` tiene su propio guard de tamaño (`DETECT_INDENT_SIZE_LIMIT`, `indent.ts`), independiente del `HIGHLIGHT_SIZE_LIMIT` de `main.ts`.** Mismo valor (10 MB) y misma razón — el `split("\n")` sobre el texto completo no es gratis para un archivo grande — pero declarado aparte a propósito: es un límite de perf de este scan puntual, no la política de highlighting del editor. Que hoy coincidan no significa que tengan que quedar acoplados; no "unificarlos" importando uno desde el otro sin releer esto.
35. **`restoreSession()` avisa con un diálogo de error igual que `openFile()`, no falla en silencio total.** "Deliberadamente silenciosos" (invariante #3 de `CLAUDE.md`) se refiere a que `restoreSession()`/`reloadFromDisk()` se saltan los guards de `confirmDiscard`/`confirmExternalReplace` — no a tragarse errores sin avisar, que es un eje distinto. Si el último archivo de la sesión desapareció o perdió permisos entre lanzamientos, antes el usuario veía un "untitled" vacío sin ninguna pista de qué pasó; ahora ve el mismo diálogo de error que `openFile()` (`message(String(err), ...)`) antes de olvidar la entrada de recientes.
36. **`saveFile()` no escribe si `doc.dirty` es `false`.** El fallback a Windows-1252 (trampa #9 / ROADMAP sección 7 ítem 1) nunca falla al decodificar, así que abrir un binario por error no da ningún error — y sin este guard, un `Mod+S` reflejo sin haber editado nada reescribía el archivo original como "texto" en UTF-8, corrompiéndolo. El guard va DESPUÉS del chequeo de `doc.path === null || doc.missing` (esos casos siempre necesitan `saveFileAs()`, tengan o no contenido). `confirmOpenBinary()` (basado en `likely_binary`, ver trampa #9) es la otra mitad de la defensa, pero solo corre en `openFile()` — `restoreSession()` la salta a propósito (mismo criterio que el resto de sus guards, ver invariante #3 de `CLAUDE.md`), así que el guard de `dirty` es el que también cubre reabrir un binario al reiniciar la app.
37. **`doc.gen`/`isStale()` es la guarda de los flujos de FONDO, no de todos.** `beginDocument()` incrementa `doc.gen` cada vez que el buffer pasa a ser OTRO documento (siempre vía `becomeDocument()`, después del último `await` del flujo). Lo capturan solo los dos flujos que no pueden esperar su turno en la cola (trampa #56): el stat de `checkExternalChange()` (después del `file_mtime` y en el `catch`; y al entrar a la cola, porque para cuando llega su turno el documento pudo cambiar) y `autosaveTick()` (trampa #52). Historia: hasta 2026-08-25 el contador se aplicaba flujo por flujo ("capturá `gen` antes de cada `await`"), lo que arreglaba los dos bugs concretos — `checkExternalChange()` asignaba el mtime del archivo VIEJO al doc nuevo, `reloadFromDisk()` metía el contenido del viejo en el buffer del nuevo — pero era una disciplina que cada flujo nuevo tenía que recordar, la misma categoría de invariante que el `refreshMtime()` eliminado en la trampa #44. La cola colapsa esa clase entera; `gen` queda para lo que la cola no puede cubrir.
38. **`init()` registra polling, autosave y el listener de `focus` ANTES de `startup_file()`, va envuelto en `try/catch`, y es el PRIMER ítem de la cola (`void exclusive(init)`).** Si `startup_file` rechazaba con los timers registrados después, la sesión entera quedaba sin red de seguridad y sin síntoma. Encolar `init()` hace que un `open-file` que llegue durante el arranque espere a `restoreSession()` en vez de correr concurrente. Adentro de `init()` se llaman las `runOpenFile`/`runOpenNewFileAt` (no las públicas): encolar desde adentro de la cola es un deadlock. La mitad ANTERIOR del arranque (evento emitido antes de que exista `listen()`) la cubre `PendingState`, trampa #32 — no esta.
39. **`saveFileAs()` limpia el recovery del path VIEJO, no solo del nuevo.** `writeTo(pathB)` limpia el recovery de B; el de A (escrito por `autosaveTick` mientras A estaba dirty) quedaba huérfano, y al reabrir A ofrecía "¿recuperar cambios?" con contenido que ya estaba guardado como B. Se captura `doc.path` antes del `writeTo` y se limpia si difiere del destino. Save As también llama `beginDocument()`: mismo buffer, distinta identidad — un poll en vuelo sobre A no tiene que aplicarle su resultado a B.
40. **`write_file` hace `sync_all()` sobre el temp antes del `rename`.** "Temp + rename" solo garantiza que un CRASH DEL PROCESO no deje el archivo roto; ante un corte de luz o kernel panic, ext4 y APFS pueden confirmar el rename en disco antes que los datos del temp, y el usuario encuentra un archivo "guardado" de 0 bytes. El `fsync` cierra esa ventana; cuesta una syscall por guardado (imperceptible para un editor de un archivo). `save_recovery` NO lo hace a propósito: ahí perder un snapshot solo significa recuperar uno más viejo.
41. **El temp del guardado se crea con el modo del original desde el primer byte, y se borra cualquier temp huérfano antes.** `std::fs::write` creaba el temp con el umask (0644 típico) y recién después copiaba los permisos: un `.env` o `~/.ssh/config` 0600 quedaba legible para todos en su mismo directorio unos milisegundos. `OpenOptions::mode(original)` lo evita; como el modo de creación pasa por umask (solo puede quitar bits), después se re-aplica `set_permissions` exacto. `create_new(true)` evita seguir un temp-symlink ajeno, y por eso mismo un temp huérfano de un crash anterior haría fallar el guardado con `AlreadyExists` — se hace `remove_file` del temp antes de crearlo.
42. **`recovery/` es 0700 y cada snapshot 0600.** Ahí cae una copia de CUALQUIER buffer dirty — incluido un archivo de secretos 0600 — fuera del directorio del original, donde los permisos del original no aplican. Antes salían 0644 vía `std::fs::write`. El `set_permissions(0o700)` corre en cada `recovery_dir()` para endurecer también un directorio creado por una versión anterior. La barrida de snapshots huérfanos es la trampa #49.
43. **El CSP está activo (`tauri.conf.json` → `app.security.csp`), con `style-src 'unsafe-inline'` como única concesión.** Los comandos `read_file`/`write_file` aceptan cualquier path con los privilegios del usuario — correcto para un editor (el diálogo del OS ES la autorización) — así que la seguridad descansa en que el webview sea confiable, y el CSP es la única defensa barata contra una dependencia npm comprometida inyectando `<script>`. `'unsafe-inline'` en estilos es obligatorio: CodeMirror inyecta `<style>` dinámicos (style-mod) que un `style-src 'self'` bloquearía; scripts inline NO se permiten. `devCsp` agrega el websocket/HTTP de HMR de Vite (`localhost:1420`), que en producción no existe. Si al agregar una dependencia algo deja de renderizar, el primer lugar a mirar es la consola del webview buscando "Content Security Policy".
44. **Ningún flujo hace un stat aparte para conocer el mtime: `write_file` Y `read_file` lo devuelven.** `refreshMtime()` no existe más. Del lado del guardado (2026-08-25, primera ronda): entre `write_file` y un `file_mtime` posterior había dos `await`, y un poll en ese gap veía mtime nuevo ≠ `doc.mtime` con `dirty = false` → reload del propio guardado (buffer reemplazado con contenido idéntico, entrada fantasma en el undo); ahora `writeTo()` asigna `doc.mtime` en el mismo tick que decide `dirty`. Del lado de la apertura (misma fecha, segunda ronda): `afterFileLoaded()` hacía `await applyLanguage()` (import dinámico, cientos de ms en frío) ANTES del stat, así que dos aperturas rápidas dejaban dos stats en vuelo y el mtime de A caía en B; peor, era un TOCTOU read→stat — un cambio entre ambos quedaba registrado como "ya visto" y nunca se detectaba. Ahora `read_file` toma el mtime del MISMO `metadata` que usa para el chequeo de tamaño, o sea ANTES de leer los bytes: si el archivo cambia entre stat y read, el contenido es más nuevo que el mtime registrado y el próximo poll recarga (inofensivo, mismo contenido). `DecodedFile.mtime` entra a `doc` por `fromDisk()`. Un invariante "acordate de X después de Y" es un return value que falta.
45. **Regla única: TODO comando de IO es `async fn`** — `read_file`, `write_file`, `file_mtime`, `save_recovery`, `read_recovery`, `clear_recovery`. En Tauri 2 un comando sync corre en el main thread (el de la UI); con `async` va al runtime tokio y el bloqueo cae en un worker, sin `spawn_blocking` ni helpers async (`fs_ops`/`text_io` siguen síncronos y testeables). `file_mtime` en particular corre cada 2 s y en cada `focus`: un stat sobre NFS/SMB colgado o un archivo evictado por iCloud congelaba la UI. Quedan sync a propósito `startup_file` (instantáneo, corre una vez), `signal_ready` e `install_cli_command` (su bloqueo durante el prompt de admin es deliberado, ver comentario en el código). Consecuencia del lado TS: el usuario puede tipear DURANTE un guardado — ver trampa #51.
46. **`startup_file()` usa `args_os()` y `resolve_open_arg` recibe `&Path`; un path resuelto que no es UTF-8 es un ERROR tipado, no un target lossy.** En Linux argv son bytes y `std::env::args()` hace panic. Hasta 2026-08-25 el resultado se hacía `to_string_lossy()`: un path con U+FFFD hacía que `read_file` dijera "does not exist" sobre un archivo que existe, y encima lo olvidaba de recientes. Ahora `utf8_path` chequea el path **resuelto** (no el argumento — un symlink puede canonicalizar a bytes crudos aunque el arg sea UTF-8) y devuelve `NonUtf8Path`; `startup_file` lo convierte en `Err(String)` (el `try/catch` de `init()` lo muestra) y single-instance/`Opened` lo emiten como evento `open-file-error` (payload: la oración lista para mostrar; `main.ts` la encola en `openFileQueue` para que no se superponga a otro diálogo). El callback de single-instance sigue sin poder blindarse: el plugin llama `std::env::args()` en el segundo proceso — el panic es de ese proceso, no del nuestro.
47. **Un `\r` suelto (Mac clásico) se normaliza a `\n` como siempre, pero ahora CUENTA en `detect_eol`.** Cualquier presencia de CR-only pone `mixed_eol = true`, y un archivo 100% CR reporta `eol: "LF"` + `mixed_eol: true`. No es un tercer estilo de guardado a propósito — portable-editor solo escribe LF o CRLF — así que ese archivo VA a ser reescrito como LF al guardar; el "(mixed)" de la status bar es el único aviso honesto de que la conversión es irreversible. Antes la conversión era silenciosa. Tests en `text_io.rs`.
48. **`is_stale_symlink` solo considera "nuestro" un symlink cuyo destino (`read_link`) tiene el mismo `file_name` que el ejecutable que estamos por linkear (`current_exe()`).** Se compara el nombre y no el path completo porque el bundle viejo puede vivir en otro lado (`~/Applications` vs `/Applications`, o un build de dev en `target/`): un path distinto sigue siendo nuestro link, roto o desactualizado. Un symlink que apunta a otro binario ya no se borra en silencio: cae al camino de `osascript`, que igual hace `ln -sf` — comportamiento preexistente, pero ahora la decisión de pisar algo ajeno la toma el usuario con su contraseña, no nosotros.
49. **Al arrancar (`setup`) se barren de `recovery/` los snapshots con mtime de más de `RECOVERY_MAX_AGE_DAYS` (30) días.** Sin esto un snapshot huérfano (original borrado o renombrado) vivía para siempre: `clear_recovery` solo corre al guardar o descartar ESE path, y nadie vuelve a abrir un path que ya no existe. El barrido (`sweep_stale_recovery`, `lib.rs`) es best-effort (todo error se ignora: un GC fallido cuesta disco, un arranque fallido cuesta el editor), solo toca archivos regulares (nunca sigue un symlink), y corre en `setup` y no en `recovery_dir()` porque esa función se llama en cada tick de `save_recovery`. La decisión pura es `recovery::is_stale`, con test; un mtime en el futuro (reloj corrido, backup restaurado) nunca es stale.
50. **Los comandos de IO de archivo (`read_file`, `write_file`, `file_mtime`, `*_recovery`) no rechazan con un string sino con `IoError` (`io_error.rs`), serializado como `{ kind, ...campos }`** (`not_found` | `permission_denied` | `too_large { size, limit }` | `other { message }`). El texto que ve el usuario se arma en `src/io-error.ts` (`describeIoError`), no en Rust: los strings de UI ya vivían todos en el frontend, y un string armado en Rust obligaba a hacer `includes(...)` para distinguir "no existe" de "sin permiso" de "muy grande". Un comando nuevo que toque el filesystem debe devolver `Result<_, IoError>` (con `?` alcanza: hay `From<io::Error>` y `From<tauri::Error>`), y su call site en `main.ts` pasar el error por `errorMessage(err, path)` — nunca `String(err)`, que imprimiría `[object Object]`. Los comandos que no son IO (`install_cli_command`, `startup_file`) siguen con `String` y caen en el fallback del mismo helper.
51. **`writeTo()` decide `dirty` DESPUÉS del `await`, comparando el buffer actual con lo escrito (`afterWrite` en `document.ts`).** Con los comandos de IO `async` (trampa #45) el usuario puede seguir tipeando mientras el write está en vuelo; hasta 2026-08-25 `writeTo` ponía `dirty = false` incondicional y esos caracteres quedaban marcados "guardados": cerrar no confirmaba, el autosave no corría, no existían en ningún lado. `afterWrite(written, current)` deja `dirty = current !== written`, `savedText = written` (el baseline del undo es lo que está en disco, no la pantalla), `encoding = UTF-8` y `mixedEol = false` (el disco es uniforme después de guardar — mostrar "(mixed)" después sería mentir). El recovery solo se limpia si quedó limpio. Es la misma guarda que `reloadFromDisk()` tiene del lado de lectura (trampa #25).
52. **`autosaveTick()` limpia su propio snapshot si `isStale(gen) || !doc.dirty` después de su `await`.** La versión anterior (`!doc.dirty && doc.path === path`) cubría un guardado real pero no un Save As ni un descarte: el snapshot viejo de A aterrizaba DESPUÉS del `clearRecovery(A)` y, como `doc.path` ya era B, nadie lo limpiaba — reabrir A ofrecía "¿recuperar?" con contenido ya guardado como B (el leak del ítem 3 de §8 por la puerta de atrás). La regla legible: "salvo que ESTE mismo documento siga dirty, lo que acabo de escribir es basura".
53. **Cerrar la ventana con "Discard" limpia el recovery, y lo espera.** `newFile`/`openFile`/`openNewFileAt` ya hacían `clearRecovery(doc.path)` al descartar; `onCloseRequested` no, y el próximo arranque decía "portable-editor didn't close cleanly … recover?" para cambios tirados a propósito — mensaje falso además. Se hace `await` (no `void`): la ventana no tiene que bajar con el delete en vuelo.
54. **`forgetRecent` solo ante `not_found`.** Un archivo demasiado grande, sin permiso, o en un volumen todavía no montado sigue existiendo: olvidarlo de recientes (y con `restoreSession`, mostrarle un error y olvidarlo) castigaba al usuario por un estado transitorio. Con el error tipado (trampa #50) es una condición de una línea (`isGone`).
55. **`DecodedFile` vive en `document.ts`, no en `ipc.ts`.** Es "lo que el disco dice de un documento"; `ipc.ts` solo lo transporta. Antes había un ciclo type-only (`document.ts` → `ipc.ts` → `document.ts`): se borraba en runtime, pero la flecha del módulo puro apuntaba al de IPC. Mismo criterio para `afterFileLoaded()`: ya no toca `doc.path`/`doc.missing` — todo caller pasa antes por `becomeDocument()` (Save As incluido, con `{ ...doc, path, missing: false }`).
56. **Por qué una cola y no más `gen`: los diálogos de Tauri son async y el event loop sigue vivo con el sheet arriba.** Un drop, un `open-file`, un clic en recientes o un poll podían aterrizar con un "discard A?" abierto, y la respuesta del usuario se aplicaba al documento que estuviera en pantalla en ESE momento — no al que consintió. Casos reales encontrados en la segunda revisión: (a) la rama ASK de `checkExternalChange()` no tenía `isStale` entre `confirmReloadDiscard()` y `reloadFromDisk()`: soltar B (dirty por recovery) con el diálogo de A abierto y responder "Reload" recargaba B y le borraba el snapshot; (b) `newFile`/`openNewFileAt`: `await confirmDiscard()` → `becomeDocument()` sin verificar que el doc consentido siguiera en pantalla. Agregar `gen` a cada uno era seguir pagando la disciplina; serializar (`exclusive()`) hace que adentro de un flujo el documento NO PUEDA cambiar bajo sus `await`, así que `reloadFromDisk()` ya no tiene ninguna guarda. El poll encola sus dos ramas de recarga (RELOAD y ASK) con un `isStale(gen)` al ENTRAR — para cuando le toca el turno, el usuario pudo haber abierto otra cosa — y, de yapa, ya no apila una segunda pregunta contradictoria sobre un "discard?" abierto. Regla operativa: las entradas públicas (`newFile`, `openFile`, `saveFile`, `saveFileAs`) encolan; desde adentro de un flujo encolado se llama a las `run*`.

## Verificación

- Frontend: `npm run lint` (Biome), `npm run typecheck` (tsc) y `npm run test` (Vitest) — los tres en verde antes de dar por bueno un cambio.
- Rust: `cargo fmt` local; `cargo clippy -- -D warnings` y `cargo test` corren en CI (ambos compilan, así que localmente los corre el dev cuando quiere).
- CI (`.github/workflows/ci.yml`): todo lo anterior en cada push/PR a main. El workflow de release es aparte (`release.yml`).
- La lógica pura testeable vive separada del wiring: `src/document.ts`, `src/recent.ts`, `src/prefs.ts`, `src/paths.ts`, `src/indent.ts` (sin DOM ni Tauri) con sus `*.test.ts` al lado. `src/ipc.ts` es el único módulo del frontend que importa `@tauri-apps/api/core`. `main.ts` solo orquesta. Del lado Rust, lo mismo: `text_io.rs`, `recovery.rs`, `fs_ops.rs` y `startup.rs` reciben `&Path`/bytes (nunca `AppHandle`) y llevan sus tests en `#[cfg(test)]` (los de filesystem usan `tempfile`, dev-dependency); `lib.rs` solo cablea.
